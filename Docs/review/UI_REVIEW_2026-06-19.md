## 0. The reframing that organizes this review

The most important signal in the codebase is the 2026-06-17 buyer demo: **a real buyer rejected the product on trust, complexity, and value clarity** — not on missing features. The two follow-up notes (`2026-06-18`, `2026-06-19`) document the same three objections surviving four passes of fixes.

That reframes the UI's job. The product's #1 problem is **not the feature gap inventory** (which is large but tracked). The #1 problem is **cognitive load and trust surface area**: the UI shows the operator everything the system can do instead of the one thing the operator currently needs to know.

This review therefore weights findings by their effect on *operator legibility and trust*, not by feature completeness. A feature that exists but is illegible is scored harder than a feature that is missing.

---

## 1. First principles — what the UI must be

A security digital twin's UI has exactly four jobs, in priority order:

1. **Make the current security posture legible at a glance.** Within ~2 seconds of opening any scene, the operator must know: are we covered, where are we blind, how bad is it.
2. **Make cause legible on edit.** When the operator moves a camera, the *why* of the coverage change must be visible in the same gesture, not three panels away.
3. **Make the proposed change defensible.** Every recommendation, fix, or AI proposal must arrive with verified delta + source, in language a non-engineer buyer can repeat upward.
4. **Stay honest about what is computed vs assumed vs unknown.** Truth labels everywhere, weighted to their decision impact.

The product thesis (repo `AGENTS.md`): *"Every edit updates the risk map. The simulation must feel alive."*

The test the UI is currently failing is not the simulation (the engine is strong, ~10.8ms / 40×28 / 2 cameras, golden-claim tests passing) — it is the **connection between edit and impact in time and space**. The five verbs of the core loop (`Edit → recompute → show impact → explain → recommend`) are all implemented; they are not *visually connected*.

## 2. Diagnosis by grouping

Severity key: 🔴 critical (blocks buyer trust / contradicts product thesis) · 🟠 important (degrades operator experience or violates canonical rules) · 🟡 polish (visual / coherence).

### Group A — Trust & confidence surface  🔴

This group is the highest-severity finding in the review. It is what lost the 06-17 buyer and is only partially patched.

**A1. Confidence language is untrustworthy.**
- `Docs/notes/sentineltwin_issue_review_2026-06-18.md:42-52` documents `100% confidence` displayed next to severe warnings and implausible wall counts.
- A point-confidence number that reads `100%` adjacent to a red warning is not a confidence score — it is a false claim the UI is making. This violates `motto_v3 §0.11` (customer-facing claims) and `§0.2` (confidence honesty).
- The 06-18/06-19 fix passes added source-profile hints, raw-vs-kept counts, and lock badges — they made confidence *legible to an engineer*. They did not change the *number itself* or its visual weight. A buyer still sees a confident-looking number next to a warning.
- **Root cause:** confidence is rendered as a scalar with no source decomposition and no unresolved-warning gating.

**A2. Truth labels exist but carry the wrong visual weight.**
- CURRENT_IMPLEMENTATION_STATE (`11) Truth labeling and trust-audit coverage`) confirms `Truth: Simulated` / `Truth: Computed` / `Truth: Live` are wired in Metrics / Report / StatusBar.
- They render as small footer chrome. On any number that drives a decision, the truth label should be the dominant visual signal, not the smallest text on the panel.
- **Root cause:** truth labels were added as a trust-audit compliance pass, not as a primary legibility primitive.

**A3. Detector-vs-operator source-of-truth is visually ambiguous in floor-plan flow.**
- The 06-17 trust break was literally this: user enters known dimensions, system overwrites them after Apply Calibration.
- The fix made calibration authoritative (`floor-plan-import.ts`, `ImportReview.tsx`) and added a lock badge + from→to delta message — but the *values themselves* don't carry a distinct visual treatment. A locked dimension and a derived dimension still look like the same kind of number on the same kind of field.
- **Root cause:** "authoritative" was implemented as a data-layer contract; the UI layer did not get a corresponding visual grammar for "user-owned vs system-derived."

### Group B — Cognitive load / density  🔴

**B1. The bottom panel exposes ~19 tabs across 4 groups.**
- Verified: `apps/studio/src/components/bottom-panel/BottomPanel.tsx:51-77`.
  - `TABS` array: 19 entries (`outcome`, `metrics`, `issues`, `sensors`, `redundancy`, `counterfactual`, `threat`, `novel`, `scenario`, `budgeting`, `report`, `assumptions`, `governance`, `provenance`, `timeline`, `temporal`, `beforeafter`, `help`, `debug`).
  - `TAB_GROUPS`: Analysis (10), Report (4), Timeline (3), Dev (2).
- The grouping is already half-built — the structural fix (planes) is mostly navigational, not inventive (see Part 3).
- 19 tabs is not a panel. It is a second application hidden behind a tab strip. No operator can hold 19 verbs in working memory.

**B2. The dashboard home has 11 toggleable sections plus 4 competing navigation lists.**
- Verified: `apps/studio/src/components/launcher/StudioDashboardHome.tsx:99-111` (`DASHBOARD_SECTION_ITEMS`, 11 entries).
- Plus `NAV_ITEMS` (6, line 52), `WORKSPACE_MODE_ITEMS` (6, line 61), plus the launcher's own quick-start / library / search / issues / assumptions / project-settings panels.
- The design-pack target (`StudioDashboardHome_CurrentWorkspacePreview_RiskStatusPanel.png`) is *simpler* than what shipped. We overshot the target and added density the reference never asked for.

**B3. Three independent navigation grammars.**
- Verified: `ProductView` (`apps/studio/src/store/product-view-store.ts:11-25`, 14 states), `ViewMode` (`StudioShell` view modes: map / camera_view / wall / replay / compare / report / analytics, 7 states), and the 19-tab bottom panel — three separate navigation systems.
- The design pack imagined **one** left rail + **one** mode strip. The live app has three grammars that overlap (e.g. `audit_report` exists in `ProductView` *and* `report` exists in `ViewMode` *and* `REPORT LITE` exists as a bottom tab).
- An operator must learn all three to navigate. This is the "too complicated" objection in concrete form.

**B4. Every feature is permanently visible — *the contextual layer exists, the rendering layer ignores it.***
- `motto_v3 §11`: *"Do not delete overbuilt features... hide them from the UI instead of deleting the code."* The codebase already respects the "don't delete" half. The work is the *arrangement* half: features should be shown by contextual relevance, not removed.
- Verified: the contextual surfacing infrastructure is substantially built:
  - `enabledAnalysisModules` (`apps/studio/src/store/slices/core/layout-slice.ts:208`) — per-tab enable/disable is already a store field.
  - `buildContextualSelectionPatch` (`apps/studio/src/store/slices/core/scene-slice.ts:686-737`) — already routes inspector tab, right-panel mode, *and bottom tab* by selected node type. Camera selection → camera-relevant tab; zone selection → zone-relevant tab. The mapping exists; the chrome doesn't reflect it.
  - `contextualBottomTabForNode` (`scene-slice.ts:624`) and `getFirstEnabledAnalysisTab` (`scene-slice.ts:681`) — node-type → bottom-tab resolution already implemented.
  - `dockAttention` (`layout-slice.ts:317`) — already flags which dock wants attention per side.
  - `visibleComponents` + `VIEW_MODE_PRESETS` (`lib/studio-constants.ts:15`) — per-view-mode component visibility already wired.
  - `WorkspacePresetSwitcher` (`apps/studio/src/components/dock/WorkspacePresetSwitcher.tsx:51`) — already reads `enabledAnalysisModules`.
- **So the problem is not "features are visible that shouldn't be." It is "the system already knows which features matter for the current context, and the rendering layer renders all 19 tabs flat regardless."** Governance, Sensors, ONVIF, Provider Governance, Model Eval Suite, Support Delivery, Identity Conflict — all earned their place. They should appear/surface/contextualize based on what the operator is doing (a governance review, a sensor binding task, a multi-seat shared-workspace moment), not be permanently co-equal with Metrics on every screen.
- This converts B4 from a "hide things" task into a "wire the rendering grammar to the contextual layer that already exists" task — feature-preserving by construction.

### Group C — The core loop doesn't pulse  🟠

The five verbs are implemented (`Edit → recompute → show impact → explain → recommend`) but not *connected in time*.

**C1. No live "what changed" affordance after an edit.**
- `use-simulation.ts` debounces recompute to 400ms (CURRENT_IMPLEMENTATION_STATE).
- After recompute, the metrics cards silently update. The operator has to mentally diff.
- Compare mode already has the right pattern: `DeltaMetricsBar` (5 delta chips — Overall Coverage / Recognition Quality / Blind Spot / Camera Count / Critical Zones) in `CompareView.tsx`. That pattern should be *ambient in Map View* after every edit, not only in Compare.

**C2. Recommendations are divorced from the edit that triggered them.**
- `IssuesTab` lists issues with `Preview Fix` / `Apply Fix` / `Revert Preview` / `Test Fix` (confirmed in CURRENT_IMPLEMENTATION_STATE).
- No causal line connects "I just moved Camera 2" → "this specific issue improved/regressed." The fix exists in Compare; it should be a lightweight inline thread in Map View.

**C3. "AI proposes, simulation verifies" is architecturally true but visually absent.**
- This is the canonical rule (`AGENTS.md` → Canonical Rules) and the product's primary differentiator.
- In the UI, an AI-suggested scene change looks identical to a manual edit. There is no visual grammar for "this is an AI proposal pending your verification" — no distinct color, no pending state, no "verify now" affordance.
- The Provider Governance / Model Eval surfaces (Debug tab) expose the *plumbing* of AI; the *experience* of receiving an AI proposal has no visual treatment.

## 3. Long-term direction — four options

Per the user's direction, the long-term direction is presented as **four options**, not a mandated north star. **All four are feature-preserving** — none delete features or logic; the question is how features are arranged and surfaced.

### Option 1 — Three-plane re-architecture (Risk / Authoring / Evidence)  *recommended*

Re-organize the entire UI around three planes rather than the current dock-grid:

- **Risk Plane (always on, dominant).** Coverage posture, blind spots, failing zones, temporal risk. The persistent visual ground. Answers "am I safe right now."
- **Authoring Plane (summoned).** Editing cameras, walls, paths, zones. Appears when the operator engages an edit intent; recedes when done. Today, authoring tools and analysis share the canvas permanently.
- **Evidence Plane (summoned).** Provenance, governance, reports, sensor/ONVIF, support handoff. Today these live in the same bottom tab strip as Metrics.

**Why this fits:** The 19-tab problem collapses structurally. The existing `TAB_GROUPS` (`BottomPanel.tsx:73-77`) already map cleanly — Analysis → Risk, (new) → Authoring, Report+Dev → Evidence. The structural work is mostly navigational.

**Why this is bold:** It changes the product's visual identity from "CAD editor with security overlays" toward "security operations console with an edit mode" — which is closer to the thesis ("not a CCTV planner", "live security digital twin").

**Cost:** Multi-pass. Affects `StudioShell`, `BottomPanel`, `ContextRightPanel`, `LeftPanel`, view-mode semantics. Not a one-session change.

**Rejected-by-default alternative:** tab-consolidation-only (Option 2). Cheaper, but does not fix the deeper issue that authoring and analysis share the canvas.

### Option 2 — Tab consolidation only (no plane change)

Collapse the 19 bottom tabs into the existing 4 groups (Analysis / Report / Timeline / Dev) as a two-level nav: pick a group, then pick a tab. Default-hide Dev entirely behind an operator disclosure.

**Why this fits:** Lowest disruption. The grouping already exists in code. The 06-17 "too complicated" objection gets partially answered.

**Why this falls short:** It treats the symptom (tab count) not the cause (authoring and analysis share the canvas). The operator still cannot tell whether they are in "I am editing" or "I am reviewing."

**Cost:** Single pass. Affects `BottomPanel.tsx` rendering and the tab-strip component.

### Option 3 — Workspace presets as the primary navigator

Promote `workspacePreset` (already in store) to the primary navigation surface. Each preset (Coverage / Camera View / Camera Wall / Path Replay / Compare / Report / Analytics) carries its *own* curated subset of bottom-panel tabs and dock configuration. The mode strip becomes the navigator; the bottom panel becomes mode-dependent.

**Why this fits:** Presets already exist (`VIEW_MODE_PRESETS`, `lib/studio-constants.ts`). The ViewModeBar already does some of this. Pushing it further means each mode advertises its own analysis surface instead of all 19 tabs being available everywhere.

**Why this falls short:** Does not address the dashboard density (B2) or the three-navigation-grammar problem (B3) directly. Presets are studio-only; intake is unaffected.

**Cost:** Medium. Per-mode tab manifests need to be authored and maintained.

### Option 4 — Contextual priority (connect the rendering layer to the contextual layer that already exists)  *closest to the product's existing architecture*

Don't re-architect at all. Instead, make the rendering grammar reflect the contextual relevance layer the store already computes. The infrastructure is verified present (see finding B4): `buildContextualSelectionPatch`, `contextualBottomTabForNode`, `getFirstEnabledAnalysisTab`, `dockAttention`, `enabledAnalysisModules`, `visibleComponents`, `VIEW_MODE_PRESETS`.

The change: the 19-tab strip stops being a flat alphabetical group render and becomes a **contextually-prioritized render**:
- A short foreground row of tabs relevant to the current selection + view mode + active workflow (e.g. camera selected → Camera-relevant + Metrics + Issues foregrounded; governance review active → Governance + Evidence foregrounded).
- A single "more" affordance for the remaining tabs — reachable in one interaction, never deleted.
- `dockAttention` already flags which dock wants attention; extend the same idea to flag which *tabs* want attention when simulation/selection changes.

**Why this fits:** No new navigation system. No re-architecture. No feature removal. It is purely "render the existing contextual truth instead of rendering everything flat." The hardest part (computing what's relevant) is already done; only the display layer needs to honor it.

**Why this is likely the right answer for V1:** Options 1–3 all change the product's navigation grammar and demand operator re-learning. Option 4 preserves the existing grammar and only changes *what is foregrounded*. It also scales: as more operator-grade features land, they slot into the contextual-priority model rather than worsening a flat strip.

**Why this might fall short:** Option 4 alone does not fix the three-navigation-grammar problem (B3) or the dashboard density (B2). It is the right answer for *the bottom panel*; it does not by itself fix *the dashboard home* or *intake*.

**Cost:** Lowest of the four against the bottom-panel problem. Affects `BottomPanel.tsx` rendering layer + extending the existing contextual selectors to drive tab priority. D2 (unify navigation grammars) is still needed separately for B3.

**Recommendation:** Option 4 for the bottom-panel density problem (B1/B4). Pair it with D2 (navigation reconciliation) for B3 and dashboard-section contextualization for B2. Option 1 (3-plane) remains a valid longer-term evolution *on top of* Option 4 — if the contextual-priority model proves insufficient, the 3-plane split is the natural next step. But Option 4 should be tried first because it is the lowest-disruption, highest-fidelity-to-existing-architecture path.

### Recommendation

**Option 4 (contextual priority) is the recommended first move** for the bottom-panel density problem because it requires no re-architecture, removes no features, and connects rendering to contextual truth the store already computes. **Option 1 (3-plane) remains available as a later evolution** if Option 4 proves insufficient — but try Option 4 first because it is the path that preserves the existing grammar and architecture.

D2 (unify navigation grammars) and dashboard-section contextualization are needed independently of which option is chosen for the bottom panel. The full Density Pass therefore composes: Option 4 (panel) + D2 (nav reconciliation) + contextual dashboard sections (B2), all feature-preserving. **Final architectural commitment should follow a dedicated brainstorm** — this review documents the directions, it does not pre-approve the build.

## 4. New improvements — prioritized passes

Organized into five passes so they can ship as coherent units. Each item names its files and the concrete change.

### Trust Pass (T) — fixes the buyer trust break

- **T1 — Honest confidence renderer.** Replace point-confidence scalars with banded, source-tagged confidence ("Low / Medium / High — N detector candidates, M unresolved warnings"). Hard rule: ban `100%` whenever any unresolved warning exists. Affects `ImportReview.tsx`, `floor-plan-import.ts` (output), and any surface displaying detector confidence. *Directly fixes 06-17 failure A1.*
- **T2 — Visual lock treatment for user-authoritative values.** Distinct color + icon + border for user-locked values (calibration, manual dimensions) vs derived values. Not just a badge. Affects `ImportReview.tsx` calibration card, any `lastActionMessage` value rendering. *Fixes A3.*
- **T3 — AI-proposal visual grammar.** A distinct "pending verification" treatment (color, badge, "verify now" affordance) for any AI-suggested scene change so the canonical "AI proposes, simulation verifies" rule is *visible*. Affects `use-ai-command.ts`, `AiLayoutDraftView.tsx`, any counterfactual preview surface. *Fixes C3 and enforces the product's primary differentiator.*

### Density Pass (D) — fixes the "too complicated" objection

*Framing:* this is **not** "hide features behind an Advanced drawer." That is the crude, static version and it doesn't solve the problem. The features earned their place. The task is to **arrange/surface them by contextual relevance** — connect the rendering grammar to the contextual layer that already exists in the store (see finding B4 for the verified infrastructure). Features appear when the operator's context makes them relevant, recede when it doesn't, and remain reachable on demand.

- **D1 — Render the bottom panel by contextual priority** (Option 4, recommended first move) *or* collapse into plane-switchers (Option 1) *or* a two-level group nav (Option 2). Affects `BottomPanel.tsx:51-77` rendering layer. The data model (`TAB_GROUPS`) already supports grouping; the contextual-selection layer (`scene-slice.ts:686`) already knows which tab matters — Option 4 wires the rendering to that existing layer without re-architecture.
- **D2 — Unify the three navigation grammars** (not delete any). Collapse `ProductView` (14 states), `ViewMode` (7 modes), and bottom-tabs into one left rail + one mode strip, matching the design-pack grammar. Each of the three carries real routing responsibility; the task is reconciliation into one vocabulary, not removal. Affects `product-view-store.ts`, `StudioShell.tsx`, `StudioDashboardHome.tsx`. *Fixes B3.*
- **D3 — Contextual surfacing, not static disclosure.** Wire the rendering layer to the contextual layer that already exists:
  - Tab strip shows the contextually-relevant tabs first (the ones `buildContextualSelectionPatch` and `contextualBottomTabForNode` identify for the current selection/mode), with the rest under a single "more" affordance — not deleted, prioritized.
  - Operator-grade surfaces (Governance, ONVIF live binding, Provider Governance, Model Eval Suite, Support Delivery, Identity Conflict, Sensors) surface when their trigger context is active (a governance review, a sensor binding task, a shared-workspace moment, a support handoff) and are reachable on demand otherwise via the "more" affordance or the left rail. They are never *removed*; they are *arranged*.
  - This is feature-preserving by construction: every tab remains reachable, the change is purely *which ones are foreground vs background for the current operator intent*. Per `motto_v3 §11` (hide/don't delete) — but "hide" here means contextual arrangement, not a static Advanced drawer. *Fixes B4.*

### Loop Pass (L) — makes the core loop pulse

- **L1 — Ambient edit-delta.** After any scene edit, show inline delta chips on affected metrics ("Coverage +4.2%") that fade after a few seconds. Reuse `DeltaMetricsBar` from `CompareView.tsx`. Affects `WorkspaceCanvas.tsx` overlay layer, `MetricsTab`. *Fixes C1.*
- **L2 — Causal issue threading.** Issues touched by the most recent edit float to the top of `IssuesTab` with a "changed by last edit" tag. Requires the recompute to emit a per-issue delta against the previous result. Affects `use-simulation.ts`, `IssuesTab.tsx`, store. *Fixes C2.*

### Intake Pass (I) — fixes the actual buyer path

- **I1 — One intake surface.** `SiteIntakeHub` becomes the single first-run screen. Remove the duplicate quick-start from `StudioDashboardHome`, and clearly subordinate or remove `ProjectStartLauncher`. Affects `ProductViewRouter.tsx`, `StudioDashboardHome.tsx`, `ProjectStartLauncher.tsx`. *Fixes D1.*
- **I2 — Build ScanSiteWizard as designed.** Implement the 10-step horizontal stepper from `ScanSiteWizard_GuidedCapture_RoomDimensionsOverviewPhotos.png` (room dimensions + overview photos in step 1, progress sidebar, limitation card). The current loose structure diverges from the approved design. *Fixes D2.*
- **I3 — Buyer-grade floor-plan correction.** Replace the checkbox wall list with a canvas-direct "click wall to keep / click wall to drop" interaction with running before/after stats and a visible scale bar. The checkbox list is the trust-killer. Affects `ImportReview.tsx`. *Fixes D3 and is the direct 06-17/06-19 carryover.*

### Visual Pass (V) — coherence

- **V1 — Enforce the canonical map token board as the only color source.** Lint against ad-hoc Tailwind color literals in map-adjacent components. Affects `map-colors.ts` (extend to full token set), all components currently using `MAP_COLORS.*` alongside ad-hoc literals (`ViewModeBar.tsx`, others). *Fixes E1.*
- **V2 — Three-state DockPanel collapse.** Restore collapsed = icon rail (per design-pack MiniMap board), not invisible. Affects `DockPanel.tsx:42`. *Fixes E2.*
- **V3 — Document a type scale.** One place that defines text sizes for tab labels, shortcut chips, dock headers, status bars. Affects a new `design-tokens.md` + shared utility. *Fixes E3.*

## 5. Cross-cutting observations (not findings, but worth recording)

- **The simulation engine is not the problem.** ~10.8ms / 40×28 / 2 cameras, golden-claim tests, deterministic, zero-React worker package — all verified in CURRENT_IMPLEMENTATION_STATE. The UI is under-leveraging a strong engine.
- **The trust-audit harness exists and is good.** `truth-audit` route + manifest catches placeholder drift in visible copy. It should be extended to catch confidence-language violations (T1) so the 06-17 failure cannot regress.
- **The design pack is internally consistent and under-implemented in two places:** the ScanSiteWizard guided flow (D2) and the MiniMap three-state collapse (E2). Both are documented as Primary targets and both diverge in live code.
- **Parallel-agent density is visible in the codebase.** Many of the operator-grade surfaces (ONVIF, Model Eval, Support Delivery, Identity Conflict) read like they were built by parallel agents each extending the product in a defensible direction, then all surfaced simultaneously. The cure is not deletion (per `motto_v3 §11`) — it is disclosure-based visibility (D3).

If two passes ship, add **Intake Pass I3** (buyer-grade floor-plan correction). T1 + I3 together address both halves of the 06-17 trust break: the confidence lie and the unworkable correction surface.

The Density Pass (D1/D2/D3) is the largest-leverage pass for the "too complicated" objection but is also the most disruptive. It should follow a dedicated brainstorm that commits to Option 1, 2, or 3.

The Loop Pass (L1/L2) is what makes the product *feel* like a live twin rather than an editor. It depends on Density being resolved (the metrics need a stable home before delta chips can sit on them).
